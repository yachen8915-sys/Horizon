# Horizon 信息雷达全面升级产品方案

**状态：** 已确认，进入实施规划阶段

**确认日期：** 2026-09-03

**基线：** `origin/main@907395b107b71f7ad4fe56d6f05c3d0edc4d7064`

**范围：** 本文只定义产品与系统方案，不授权修改业务代码、恢复定时任务或发送飞书。

## 1. 产品目标

Horizon 从“采集后生成一张日报卡片”升级为服务旁门账号的 AI 信息收集、判断与筛选系统。系统每天要帮助用户完成四类判断，并按以下顺序组织结果：

1. **产品与能力变化：** 哪些 AI 产品、模型、功能、工具或行业变化真的值得关注、实测或调整认知。
2. **热门内容与传播机会：** 哪些内容正在快速传播，为什么火，旁门能否形成新的内容角度。
3. **技术前沿与开源：** 哪些技术突破、论文、模型、框架或项目可能改变产品能力与创作方式。
4. **平台 AI 变化与机会：** 哪些平台功能、规则、商业化和创作者政策变化会影响运营。

其中 AI 产品与行业情报占主体，内容选题、大众热点和平台运营机会作为补充。海外信号优先；全球重大 AI 事件即使与国内的即时关联较弱，也应保留。

## 2. 验收标准

升级是否成功，优先看四项结果：

- 重大、重要、可行动的信息不应明显漏掉。
- 每日精选中至少 80% 的内容让用户认为值得打开或读完。
- 精选中不再出现明显重复、低质、未成熟或证据不足的内容。
- 来源、作者、平台和主题不能被少数对象长期垄断。

上线前必须完成连续 3 天影子运行。影子运行不推送飞书、不写生产状态，逐日检查上述四项。

## 3. 明确不做什么

- V1 不建设收藏、忽略、低质标记或自动学习偏好的反馈系统。
- V1 不立即接入飞书 Base；先建立系统内部的完整候选档案，验证确有检索和协作需求后再决定是否同步 Base。
- 不沿用“AI 应用 / AI 技术 / AI 媒体”作为最终产品主分类。
- 不用增加关键词、阈值和栏目配额继续掩盖产品结构问题。
- 不因栏目空缺而放回低质量、重复、未成熟或证据不足内容。
- 不把抓取量当作用户价值，也不把未推送候选静默丢弃。
- 不恢复 GitHub workflow、本机计划任务或正式飞书推送，直到影子验收完成并获得明确确认。

| AI 质量升级 | `6c7e8f3` 加未提交修改 | 跨栏唯一展示、爆点评分、B站门槛、来源限制 | 先盘点行为契约，再迁移或重写 |

当时实际运行状态为：GitHub `Daily Horizon Summary` 已手动禁用，本机 `\Horizon\Pangmen Daily Radar` 已禁用，没有活跃日报 Run。它们是核验日快照，上线前仍须重新核验。

当前数据流为：

`信息源 → 抓取 → 正文获取 → 互动增长观察 → URL 合并 → 可选传播硬门槛 → AI 分析 → 质量/主题去重/多样性/冷却/来源限制 → 跨栏唯一展示与爆点评分 → 栏目平衡 → 内容延展 → Markdown / Pages / 飞书`

关键结构问题不是单个阈值，而是候选在多个阶段退出后没有统一、耐久、可搜索的生命周期记录。“查看更多”仍是已入选内容的展示层，不是完整候选库。

## 5. 信息分类

每条候选只有一个主决策分类，可以带多个辅助标签。分类依据是“用户要做什么判断”，不是来源类型。

### 5.1 产品与能力变化

包括：

- 模型或产品正式发布、重大升级、能力边界变化；
- 新工具、新功能、新玩法和可复现工作流；
- 能实际测试、演示或转化为旁门内容的案例；
- 对用户成本、效率、可用性、质量或使用方式有实质影响的行业变化。

### 5.2 热门内容与传播机会

包括：

- X、YouTube 及其他平台上已形成传播的 AI 帖子、视频和创作者玩法；
- AI 圈外但可与 AI、效率、职场、创作或普通人焦虑连接的大众热点；
- 处于早期上升阶段、有足够传播信号且能说明增长原因的内容；
- 竞品账号已开始集中制作、值得判断是否跟进或差异化处理的主题。

### 5.3 技术前沿与开源

包括：

- 对产品能力或实际工作方式有影响的论文、模型和技术突破；
- 有真实代码、演示、采用或复现证据的开源项目；
- 能被非纯研发用户理解其意义的技术变化。

### 5.4 平台 AI 变化与机会

包括：

- 平台正式发布的 AI 功能、创作者工具和商业化能力；
- 影响发布、分发、版权、流量、变现或账号安全的规则变化；
- 平台生态中出现的重大机会和风险。

公司融资、纯商业竞争和组织人事不是独立主类；只有直接影响产品、技术、用户或平台决策时才进入上述分类。

## 6. 信息源矩阵

来源覆盖是本次升级的第一门禁，而不是候选池完成后的配置工作。只读审计已经确认：当前来源足以生成基础日报，但不足以稳定覆盖海外热门内容、完整官方产品变化和 GitHub 新项目。详细证据和补充顺序见：

`docs/superpowers/specs/2026-09-03-horizon-source-coverage-audit.md`

来源不是按平台平铺，而是按目标承担不同角色。

| 来源层 | 主要角色 | 典型来源 | 准入方式 |
|---|---|---|---|
| 官方一手 | 证实产品、技术、平台变化 | 官方博客、发布页、文档、变更日志、官方账号、代码仓库 | 重要性优先，不要求已有高传播量 |
| 技术一手 | 发现前沿能力和采用信号 | GitHub、Hugging Face、论文/实验室、开发者公告 | 代码/模型/论文可访问，意义可解释 |
| 社交传播 | 发现热门内容和早期上升 | X、YouTube、Reddit、Hacker News、B站及后续经验证的平台 | 必须结合时间、基线、播放/互动完整度判断成熟度 |
| 媒体与聚合 | 扩大召回、发现事件线索 | AI HOT、Google News、垂直媒体、Newsletter/RSS | 默认视为二级线索，优先回溯原始来源 |
| 国内平台热点 | 发现大众情绪和延展角度 | 微博、抖音、小红书、微信、B站热榜或公开趋势源 | 相关性和可延展性硬门槛，不因热度直接入选 |
| 平台规则 | 运营和商业化变化 | 平台公告、帮助中心、规则页、公开产品更新 | 原文差异与生效日期优先，二手信息待核实 |

新增来源前必须写清：服务哪类判断、原始性、质量门槛、抓取稳定性、使用成本、替代的旧来源，以及失败时如何降级。

实施开始前必须先满足最低来源覆盖：

- 每个核心产品实体至少有一个官方确认源和一个发现备用；
- 热门内容至少具备 AI HOT（含可回溯的 X 等跨平台线索）、YouTube 无密钥链路和一个独立社区来源；三条链路都须通过来源门禁，聚合条目必须按原始链接和原始作者计算来源身份；
- 技术前沿必须同时具备 GitHub 直接来源、Hugging Face 和社区/趋势补充；
- 国内热榜的业务失败能够被识别，关键平台缺口必须显式报告；
- 任何来源失败都不能被误报为“今日无重要内容”。

## 7. 候选生命周期

### 7.1 状态

每条候选进入统一档案并经历明确状态：

1. `discovered`：已发现，尚未完成正文与基础证据。
2. `enriched`：正文、作者、时间、来源和传播数据达到可分析要求。
3. `observing`：可能重要，但传播数据未成熟或证据仍待补充。
4. `eligible`：通过硬门槛，可参与当次竞争。
5. `selected`：进入上午精选或下午增量。
6. `held`：合格但因当次价值排序、多样性或展示预算未发送，可在新证据出现时重新竞争。
7. `merged`：与同一事件合并，保留为证据来源而非独立展示。
8. `rejected`：明确低质、无关、证据不足或成熟后传播不达标。
9. `expired`：观察窗口结束仍未达到准入条件。

所有状态转换必须保存时间、规则版本和原因码。抓取失败或 AI 失败属于处理失败，不得伪装为 `rejected`。

### 7.2 重新进入规则

旧内容出现以下任一实质变化，可以生成新的事件版本并重新竞争：

- 新功能或新版本；
- 新数据、真实测试或采用证据；
- 新观点改变了对事件的判断，而非换标题复述；
- 传播状态由未成熟变为确认上升；
- 官方确认取代此前的未核实信息。

## 8. 身份、事件和主题去重

系统分别维护四层身份，不再用一个键承担全部去重：

- `source_item_id`：平台原生条目身份；
- `canonical_url`：规范化 URL 身份；
- `event_key`：同一事实事件或同一产品更新；
- `editorial_topic_key`：用户看到会认为“又是同一选题”的主题身份。

处理规则：

- 同一事件的多篇转述合并成一条主记录，其他来源成为证据。
- 同一工具围绕同一任务的教程只保留最强代表；不同独立更新不能粗暴合并。
- 同一事件跨分类只展示一次；辅助价值通过标签表达。
- 跨日冷却针对事件版本，而不是永久屏蔽实体或工具。

## 9. 证据与事实状态

每条候选须保存主张、证据来源和事实状态：

- `confirmed`：官方原文或可复核一手证据支持；
- `corroborated`：至少两个相互独立、可信的来源一致支持；
- `reported`：可信二手来源报道，但尚无原始证据；
- `unverified`：热榜标题、搜索摘要、单一社交帖子或信息不完整；
- `disputed`：来源存在实质冲突。

“很重要但不热”的官方更新可凭决策影响入选。“很热但证据不足”的内容只能进入观察层或在精选中明确标注待核实，且数量受控，不能写成既成事实。

## 10. 评分与硬门槛

评分用于已通过硬门槛的候选排序，不能覆盖硬门槛。

### 10.1 硬门槛

以下内容不进入精选：

- 宣传话术多、没有可验证的新事实；
- 相同事件的重复转述；
- 同一工具、同一任务的教程扎堆；
- 社交内容刚发布、数据不成熟或成熟后传播质量明显不足；
- 热门但与旁门内容、AI 使用或用户决策无可解释联系；
- 证据不足、标题夸张或把二手转述当作已确认事实；
- 关键字段缺失到无法判断发布时间、来源或真实内容。

官方 RSS、产品公告和规则更新不使用播放量门槛。

### 10.2 排序维度

不同分类使用不同权重，但统一保留以下原始维度：

- 决策影响；
- 与旁门定位的相关性；
- 新颖性与实质变化；
- 证据质量；
- 可实测、可演示或可转成选题的程度；
- 传播强度、增长速度和相对基线；
- 新鲜度；
- 与当天已选内容的差异性。

最终分数必须能回溯到各维度、硬门槛结果和规则版本。

## 11. 多样性和新鲜度

热门内容不设固定条数上限，以价值竞争决定数量，但施加软约束和必要硬上限：

- 同一非官方二级作者或来源不能占据单类主体；
- 同一平台、作者、媒体和主题不能连续多日垄断；
- 当一个来源确有多条独立重大信息时允许超过软配额，但必须在 diagnostics 中解释；
- 不为满足多样性而补入低质量内容；不足时可以少发或不发。

跨日新鲜度比较的是事件是否新增实质信息。标题变化、媒体换写和普通转载不算更新。

## 12. 展示与发送

### 12.1 上午 09:00 完整精选

- 每天运行，包括周末。
- 目标 8–12 条，但这是展示目标，不是保底配额。
- 只要任一分类有合格内容就可以发送；没有合格内容则不发。
- 卡片按四类决策排序，每条同时提供“为什么值得看”的判断摘要和“发生了什么”的内容摘要。
- 每条展示来源、证据状态、发布时间和原始链接；必要时展示待核实提示。

### 12.2 下午 16:00 增量

- 只发送上午之后出现或发生实质变化的合格内容。
- 不重复上午内容；同一事件只有出现新功能、新证据、新数据或传播状态显著变化时才可再次出现。
- 没有新增合格内容则不发。

### 12.3 “查看更多”和内部候选档案

- 飞书卡片承担需要用户当天看见的精选，不承载完整候选。
- “查看更多”只用于展示已达精选标准但因卡片容量下沉的内容，不能冒充候选库。
- 完整候选、观察项、合并项、暂缓项、淘汰原因和处理失败写入内部持久档案。
- V1 提供本地可搜索导出和 diagnostics；飞书 Base 同步属于后续独立决策。

## 13. AI 与 API 成本控制

采用分层调用，质量优先但避免对明显无效候选调用昂贵模型：

1. 规则和结构化元数据完成 URL 规范化、来源识别、时间窗口和基础传播门槛。
2. 只对通过预筛的候选获取正文和补充证据。
3. AI 第一次调用负责结构化分类、主张提取、事件身份和质量维度。
4. 只有高潜候选才进行跨来源核实、语义主题去重和最终编辑判断。
5. 每次运行记录各阶段候选数、调用数、token、估算成本、缓存命中和降级路径。

模型失败时保留候选并标记 `analysis_failed`；除非规则可以确定性判断，否则不能静默淘汰。

## 14. Diagnostics、失败降级和可解释性

每次运行至少生成以下统计：

- 各来源抓取成功、失败、空结果和耗时；
- 各阶段进入、退出和剩余数量；
- 每个退出候选的状态、原因码、规则版本；
- 事件合并组、主记录和所有证据来源；
- 四类候选和入选数量；
- 来源、作者、平台、主题集中度；
- 上午已发、下午新增、跨日冷却和实质更新数量；
- AI/API 调用、token、成本和失败数；
- 卡片预算、下沉到“查看更多”的数量及任何截断风险。

必须区分：

- `no_qualified_updates`：系统正常运行，但没有合格内容；
- `collection_degraded`：部分来源失败，结果可能不完整；
- `pipeline_failed`：核心处理失败，不能生成可信精选。

只有第一种允许被解释为“今天没有值得发送的内容”。

## 15. 分支迁移策略

实施不直接在现有两个脏工作区继续堆叠，而是在 `origin/main@907395b` 上建立隔离分支：

1. 先建立候选档案、状态机、证据模型和稳定 diagnostics。
2. 再从 `e4cd9f2` 提取平台热点的有效行为与测试，不整分支合并。
3. 再从 `6c7e8f3` 和未提交质量升级提取唯一展示、爆点评分、传播硬门槛、观察池和来源限制。
4. 对冲突规则按本方案重写，不同时保留两套同义阈值。
5. 旧状态只迁移为历史基线，不制造历史候选、不补发旧闻。

每项迁移都需要行为测试证明“保留了什么、废弃了什么”。不得 reset、clean 或覆盖原脏工作区。

## 16. 测试、上线和回滚

### 16.1 测试层级

- 单元测试：状态转换、身份、证据、硬门槛、评分、多样性、下午增量。
- 契约测试：各来源字段、发布时间、作者和互动数据完整性。
- 离线回放：至少覆盖正常日、热点集中日、低信息日、来源故障日。
- 卡片快照：09:00 完整精选、16:00 增量、零合格内容、部分采集失败。
- 全量回归：完整 pytest、compileall、配置模型校验和 diff 检查。

### 16.2 影子上线

连续 3 天运行但不推送、不写生产状态。每天输出人工评审表：重大漏报、值得看比例、明显垃圾数、集中度和成本。

### 16.3 正式启用门槛

只有同时满足以下条件并得到用户明确确认后，才可逐步恢复：

- 四项验收标准通过；
- 上午和下午去重正确；
- 没有把采集失败解释成无更新；
- 状态迁移不会补发旧闻；
- 飞书卡片容量经过真实预览验收；
- workflow、计划任务和生产 Run 状态已重新核验。

### 16.4 回滚

- 新旧运行入口、状态目录和卡片版本必须可区分。
- 首次正式运行保留旧生产状态的只读快照。
- 新版异常时只禁用新版调度并恢复旧入口；不删除候选档案，不覆盖旧状态。
